# WebifyCMS Dev Tools 1.3.0 — Cleaner Code, Branded Errors

We tagged version 1.3.0 of `webifycms/dev-tools` on 18 November 2026 — a release for the shared toolkit that keeps every WebifyCMS package honest, and a good excuse to introduce it properly. If you have been following the CMS itself, this package is easy to miss: it is developer tooling, not something you can see in the admin panel. It is, however, one of the reasons the code you _can_ see stays consistent.

## What Is WebifyCMS Dev Tools?

`webifycms/dev-tools` is the shared development toolkit for WebifyCMS packages. Every package — `ext-base`, `ext-user`, the site you are reading — needs the same things during development: static analysis, a formatter, an upgrade tool, tests, and a way to inspect variables when something behaves strangely. Instead of each repository picking its own versions and writing its own configuration from scratch, they pull in one Composer dev dependency:

```bash
composer require webifycms/dev-tools --dev
```

The package requires PHP 8.4 and brings the following libraries with it:

- **`friendsofphp/php-cs-fixer`** — enforces and auto-fixes coding-style rules.
- **`phpstan/phpstan`** — static analysis, with the strict, PHPUnit and deprecation extensions included.
- **`rector/rector`** — automated, rule-based code upgrades.
- **`squizlabs/php_codesniffer`** — checks a hard 120-column line limit.
- **`symfony/var-dumper`** — the `dump()` and `dd()` helpers for quick debugging.
- **`filp/whoops`** — a better error page during development (new in 1.3.0).

Alongside the libraries, dev-tools ships shared configuration and small wrapper classes such as `Webify\Tools\Fixer` and `Webify\Tools\Rector`, so a package gets the project's defaults with a few lines of setup and can override only what it needs. When we raise the bar — stricter analysis, a new rule — the change lands in one place and reaches every package through a normal `composer update`.

## What's New in 1.3.0

### A branded Whoops error page

The headline addition is a reusable wrapper around Whoops. One call during development replaces the default error page with a WebifyCMS-branded one:

```php
use Webify\Tools\Whoops\Whoops;

(new Whoops())->register();
```

Web requests get the branded page, which shows the error, earlier errors, stack frames with source snippets, and request values — with secret-looking values hidden. Command-line runs keep Whoops' plain-text output, because a terminal cannot read HTML.

The layout lives in `templates/whoops/error.html.php` and the stylesheet and logo in `assets/`. They are read straight from the package, so there is nothing to publish into the consuming application. The bundled WebifyCMS logo is only the default: an application can supply its own image and alt text, or remove the brand entirely.

```php
(new Whoops(logo: 'https://example.test/logo.svg', logoAlt: 'Acme'))->register();
(new Whoops(logo: ''))->register(); // no logo
```

For finer control, `Webify\Tools\Whoops\Handler\WebifyPageHandler` can be used on its own, and an existing handler can be passed to the wrapper as `new Whoops($handler)`.

### Tool configs moved into `tools/` (breaking)

Every shared config now lives in a `tools/` directory instead of the package root, and packages are expected to keep their own configs there too. Because the tools no longer discover these files automatically, each Composer script names its config explicitly with `--config` or `-c`:

```bash
vendor/bin/phpstan analyse -c tools/phpstan.dist.neon
vendor/bin/php-cs-fixer fix --config=tools/.php-cs-fixer.dist.php --dry-run
vendor/bin/rector process --config=tools/rector.php --dry-run
vendor/bin/phpcs --standard=vendor/webifycms/dev-tools/tools/phpcs.xml src test
```

The old root-level paths are gone, so copied configs and include paths need a one-time update. The full path-by-path table is in the [upgrade guide](https://github.com/webifycms/dev-tools/blob/main/UPGRADE.md). Packages that only call `Webify\Tools\Fixer` or `Webify\Tools\Rector` from their own configs need no PHP changes.

### Stricter defaults and a line-length check

Two changes make the shared baseline tighter:

- The default PHPStan level moved from **8** to **10**. A package that needs a lower level can still set `level` in its own config.
- A new `tools/phpcs.xml` ruleset fails on lines longer than 120 columns. It is available on its own as `composer phpcs` and is now part of `composer code-check`, alongside analysis and style checks.

PHP-CS-Fixer's defaults also now allow a long class declaration to wrap after `extends` or `implements` instead of forcing it onto one unreadable line. The shared PHPUnit config carries the package license header, and unit tests cover the new Whoops wrapper and page handler.

## Upgrading

Update the constraint and follow the path changes in the upgrade guide:

```bash
composer require --dev webifycms/dev-tools:^1.3
```

Whoops and PHP_CodeSniffer are dependencies of the package, so they do not need separate requirements. No assets need to be copied — the error page, CSS and logo are read from `vendor/`.
